## What happened tonight, in order

1. **Symptom:** app wouldn't load on laptop or phone.
2. **Cause #1 — PM2 daemon was down.** This laptop (`MearHPLaptop`) doubles as the office server. PM2's daemon wasn't running (likely lost on a reboot), so the `whitevanops` app process was dead and nothing listened on port 3000. Fixed by resurrecting PM2 from its saved dump (`pm2 resurrect`).
3. **Made PM2 startup durable:** ran `pm2 save` + `pm2-startup install`. This registers a `HKCU\...\Run` registry key that fires `pm2 resurrect` on login — **not** a true boot-time Windows service. Decision made tonight: login-based startup is good enough for now; a real Windows service (e.g. via NSSM) was discussed as a future option if unattended-reboot resilience ever matters, but explicitly deferred.
4. **Symptom #2 (same evening):** app now reachable, but Chrome on phone (over the correct Tailscale HTTPS URL, Tailscale connected) returned a garbled "Operation System Error."
5. **Cause #2 — the real database was never restarted after the reboot.** `pm2 logs whitevanops` showed Prisma throwing `ECONNREFUSED` on every query. The app's actual production database is a **PostgreSQL 9.5** instance with its data directory living inside the project folder at `C:\Users\rober\Desktop\WhiteVanOps\pg_data`, meant to run on port 5433 — and it had no autostart mechanism at all (not PM2-managed, not a Windows service, nothing). It simply never came back after the reboot.
6. **Detour / mistake made and corrected:** before finding the real `pg_data` folder, investigation initially found `C:\Program Files\PostgreSQL\17\data` — a data directory whose binaries (`bin\postgres.exe` etc.) were missing entirely, while the data files remained. This turned out to be an **abandoned, unrelated leftover from Nov 2024** (confirmed via its own Postgres log — last activity 2024-11-22, no `wvo_user` role, no `white_van_ops` database). PostgreSQL 17 was reinstalled against it (after backing up the folder first) before realizing the mistake. That PG17 service has since been **stopped, unregistered, and removed**. Its data folder backup is at `C:\Users\rober\Desktop\pg17_data_backup_20260701_232940` — safe to delete whenever, not used by anything.
7. **Actual fix:** started the real Postgres 9.5 instance directly (`postgres.exe -D pg_data -p 5433`), verified via `psql` that the schema (22 tables incl. `_prisma_migrations`) and app credentials (`wvo_user`) work, then moved it under **PM2 management** as a new process named `whitevanops-db` so it starts/stops alongside the app the same way. Saved with `pm2 save`.
8. One more cosmetic loose end: a stray Windows error dialog was left open on screen from an early failed installer attempt (a PowerShell array-quoting bug split a `Program Files` path). Harmless, just needed clicking "OK" — confirmed unrelated to the real fix.

## Open items for next time (not urgent, nothing broken)

1. **Unattended-reboot risk still exists.** Both `whitevanops` and `whitevanops-db` only come back when someone logs into this laptop (PM2's login-hook startup, not a boot service). If a Windows Update reboot happens overnight with nobody around, the app stays down until someone logs in — same failure mode as tonight, just now it's a *known* one with a one-line fix (`pm2 resurrect` or just log in). Consider NSSM-based real Windows services for both processes if this becomes a recurring problem.
2. **Cleanup, no rush:** delete `C:\Users\rober\Desktop\pg17_data_backup_20260701_232940` once you're confident you don't need it (it's a copy of the unrelated abandoned Nov-2024 data, not your real data).
3. **Worth a calendar reminder:** this office server setup (app + real DB both riding on a personal laptop, started via PM2 login-hooks, with a stray unrelated PostgreSQL 9.5 Windows service from an old install still present) is fragile in a way that isn't obvious from the outside — anyone troubleshooting this box cold needs to know `pg_data` inside the project folder is the real database, not either Windows Postgres service. That's now written into the Setup manual, but worth remembering yourself too.
