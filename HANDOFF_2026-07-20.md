## 1. Completed: packaged login-500 fix (`fa144c4`)

**Symptom:** fresh installer, login with admin/admin → `POST /api/auth/login` 500. Only on a
*self-booting* install; invisible on the office PM2 box.

**Root cause — two stacked bugs:**

1. **Next 16 defaults to Turbopack**, which emitted a broken external require
   `require("@prisma/client-2c3a283f134fdcb6")` — a hashed name that never resolves.
2. **The standalone trace didn't copy Prisma 7's runtime packages**, and
   `outputFileTracingIncludes` is a plain file-copy that does **not** follow the deps of
   what it includes.

**Fix:** `next build --webpack` + explicit Prisma runtime closure in
`outputFileTracingIncludes` (`client`, `client-runtime-utils`, `debug`,
`driver-adapter-utils`, `adapter-pg`, `.prisma/client` — deliberately **not** `@prisma/**`,
which drags in ~95 MB of engines/studio/dev). `build` now runs `prisma generate` first, and
`electron-build.js` step 7b asserts the dirs landed.

### The lesson that cost the most time — read before debugging packaging again

**Running `.next/standalone/server.js` from inside the project does NOT reproduce packaged
isolation.** Node walks up the tree and resolves `@prisma/client` from the *project's*
`node_modules`, so the bug disappears and you get a misleading DB error instead. This caused
two misdiagnoses.

**Always test the packaged artifact in isolation:**

```powershell
$base = "<repo>\dist-electron\win-unpacked"
$env:ELECTRON_RUN_AS_NODE="1"; $env:PORT="3009"; $env:HOSTNAME="127.0.0.1"
Start-Process -FilePath "$base\WhiteVanOps.exe" -ArgumentList "`"$base\resources\nextjs\server.js`"" `
  -WorkingDirectory "$base\resources\nextjs" `
  -RedirectStandardError "$env:TEMP\wvo.err" -RedirectStandardOutput "$env:TEMP\wvo.out" -WindowStyle Hidden
# then POST /api/auth/login and read $env:TEMP\wvo.err
```

**Pass condition:** Prisma **P1001 `DatabaseNotReachable`** (dev DB off) — proves module
resolution is clean. **Any `Cannot find module` = still broken.**

Other traps hit this session:
- `npm run ... | tail` **masks the real exit code** (you get `tail`'s). Redirect to a file.
- A stale `node .next/standalone/server.js` process locks `.next\standalone` → build fails
  `EBUSY`. Kill it first.
- The customer's bundled Postgres was **healthy the whole time** — verified via the app's own
  `psql` and credentials. The DB is rarely the culprit; check module resolution first.

## 2. Designed, not built: Cloudflare Tunnel as default field access

**Spec:** `docs/superpowers/specs/2026-07-20-cgnat-tunnel-connectivity-design.md` (`1705efd`)

**Why:** the client is behind **CGNAT**, so port forwarding + DDNS is impossible — and
`MANUAL_White_Glove_Installation.md` Phase B currently *dead-ends* there. "Call the ISP for a
static IP" isn't a repeatable install step, so this was treated as a product problem, not a
one-client hack.

**Decision:** Cloudflare Tunnel as the default for **all** installs. One vendor domain
(~$10–15/yr, flat), one Cloudflare account (free), per-customer subdomains, `cloudflared` as
an auto-restarting Windows service. **$0 marginal cost per customer** — decisive because
there is **no subscription revenue**, so anything per-customer is a permanent unfunded
liability.

Rejected: paid Cloudflare tiers (do **not** increase tunnel throughput/stability — not gated
by plan; only Business ~$200/mo adds an SLA), vendor VPS (money is fine, but vendor-operated
uptime/patching is the real cost), Tailscale (per-seat; free tier not licensed for
commercial use).

**No migration needed — there are no production customers yet.** Port-forward + DDNS is
removed outright rather than grandfathered.

### Phase 0 — do this first (independent of Cloudflare; valid regardless)

Three real defects in current code, all unit-testable without a DB:

1. **`getSessionCookieOptions()` sets `secure` from a global env flag** (`REQUIRE_HTTPS`).
   `secure` is a **per-request** property, and one server serves both `http://localhost:3000`
   (Electron) and `https://` (techs) — a single flag is guaranteed wrong for one. Wrong value
   = login silently bounces to `/login` with no error.
   → Derive from `x-forwarded-proto === "https"`; **delete `REQUIRE_HTTPS` entirely.**
2. **`clearSessionCookie` drops `secure`/`httpOnly`/`sameSite`** (latent bug) — once cookies
   are `Secure`, a mismatched clear can fail to delete, breaking logout. Reuse the same options.
3. **Rate limiting collapses users into shared buckets.** `getClientIp` falls back to the
   constant `"unknown"` → *the whole company* shares 20 attempts/5 min. And shared NATs
   (office + mobile-carrier CGNAT) mean techs lock each other out at ~25 users.
   → Layered: (1) keep the existing DB-persisted per-account lockout as the real control,
   (2) add per-`(ip, username)` buckets, (3) generous per-IP ceiling (~100/5 min).
   Prefer `CF-Connecting-IP`; **never fall back to a shared constant.**

Files: `src/lib/auth.ts`, `src/lib/rateLimit.ts`, `src/app/api/auth/login/route.ts`
(+ `change-password`, `logout` call sites). Existing Vitest patterns in `auth.test.ts` apply.
