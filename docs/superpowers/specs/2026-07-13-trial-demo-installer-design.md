# Trial/Demo Installer — Design Spec

**Date:** 2026-07-13
**Status:** Approved, pending implementation plan

## Goal

Produce a fourth Electron installer variant, `WhiteVanOps-Trial-Setup.exe`, for use in sales demos. It runs on the full **Plus** feature set so a prospect can evaluate everything, then fully locks the app 30 days after first launch. Entering a purchase activation key at any time (before or after expiry) converts the install to a permanent license — Base or Plus depending on what was purchased.

This is purely additive. The existing `build:base`, `build:plus`, and `build:upgrade` installer paths, and the Base/Plus tier gating they rely on (`src/lib/license.ts`), are unchanged.

## Non-goals

- No subscription/renewal billing flow — activation keys are perpetual grants (an `expiresAt` field exists in the payload for future use but isn't exercised at launch).
- No defense against a prospect deleting `%APPDATA%\whitevanops\` to reset the trial clock. This is a vendor-installed, vendor-monitored sales demo, not mass self-serve distribution — that level of tamper resistance isn't worth the complexity.
- No change to session/JWT lifetime specifically for trial builds — the existing 7-day session length applies, with the same staleness trade-off the app already accepts for the `mustChangePassword` flow (see Enforcement below).

## 1. Trial anchor file

New file `%APPDATA%\whitevanops\trial.json`:

```json
{ "installedAt": "<ISO-8601>", "machineId": "<node-machine-id>", "sig": "<HMAC-SHA256 hex>" }
```

- `sig` = `HMAC-SHA256(LICENSE_SIGNING_SECRET, "${installedAt}:${machineId}")`, reusing the existing secret and pattern from `getBaseLicense()`/`verifyPlusLicense()` in `src/lib/license.ts`.
- Written lazily, not by the installer: a new `src/lib/trial.ts` module exposes `getTrialStatus()`, which — mirroring how `getLicense()` already self-heals the `License` DB row on first read — creates `trial.json` the first time it's called if `process.env.WVO_IS_TRIAL === "true"` and neither `trial.json` nor `trial-unlock.json` exists yet.
- `getTrialStatus()` returns `{ isTrial: boolean, daysRemaining: number, isLocked: boolean, machineId: string }`. `isLocked` is `true` when `now > installedAt + 30 days` AND `trial-unlock.json` is absent.
- Non-trial builds (`WVO_IS_TRIAL` unset): `getTrialStatus()` returns `{ isTrial: false, isLocked: false, ... }` immediately, no file I/O — zero behavior change for normal customer installs.

## 2. Activation key format

A single JSON payload format handles both purchase outcomes:

```json
{ "machineId": "<their machine's ID>", "tier": "base" | "plus", "expiresAt": null, "notes": "...", "sig": "<HMAC hex>" }
```

`sig` = `HMAC-SHA256(LICENSE_SIGNING_SECRET, "${machineId}:${tier}:${expiresAt || ""}")`.

Generated by the vendor via a new flag on the existing script:

```bash
node scripts/license-manager.js --unlock-trial --machine <machineId> --tier base|plus [--expires YYYY-MM-DD] [--notes "..."]
```

The prospect's `machineId` (from `getTrialStatus()`) is displayed on the lockout screen and in Settings so they can send it to the vendor; the vendor mints the key and sends the JSON block back.

Deliberately does **not** reuse the existing `license.json` base-key chain (`getBaseLicense()` / `verifyPlusLicense()`): that chain is not actually wired into any real customer-activation flow today (only `scripts/activate-dev.js` writes `license.json`, for local dev). Binding the trial-unlock key directly to `machineId` avoids inheriting that half-built path.

## 3. Applying the key

Extends `POST /api/license` (superuser-only, existing auth/audit pattern) with a new action:

```json
{ "action": "unlock-trial", "licenseKey": "<pasted JSON>" }
```

Handler steps:
1. Parse the payload; verify `sig` against **this machine's real** `machineIdSync()` (not the payload's claimed value — reject if they don't match), `tier`, and `expiresAt`.
2. Reject with 400 if the signature doesn't verify, or if `tier` isn't `"base"`/`"plus"`.
3. Write `trial-unlock.json` (its mere presence permanently defeats the trial lock, independent of `trial.json`'s expiry — never deleted by any code path).
4. Upsert the `License` row: `tier: payload.tier`, `expiresAt: payload.expiresAt`, `activatedAt: now`, `licenseKey: null` (no license.json chain involved).
5. `audit(user.userId, "UPDATE", "License", row.id, { action: "unlock-trial", tier: payload.tier })`.

A Base-only purchase therefore correctly **drops** the Plus features the prospect was trialing (tier reverts to `base`); a Base+Plus purchase stays on Plus.

## 4. Enforcement

The middleware (`src/middleware.ts`) is deliberately edge-safe today — no `fs`/Prisma imports, per its own comment. Trial-lock enforcement follows the exact shape of the existing `mustChangePassword` mechanism rather than adding filesystem/DB access to the edge runtime:

- At login (`POST /api/auth/login`, Node runtime), after authenticating, call `getTrialStatus()`. If `isLocked`, stamp `trialLocked: true` into the JWT payload (new claim, alongside the existing `mustChangePassword`).
- Middleware checks `payload.trialLocked` and redirects any request outside `["/trial-expired", "/api/trial-unlock"]` to `/trial-expired` — same branch shape as the existing `mustChangePassword` redirect.
- **Accepted trade-off:** sessions last 7 days (`setExpirationTime("7d")` in `src/lib/auth.ts`). A user already logged in when the trial flips to expired keeps working until their token naturally expires or they log out — up to a 7-day grace window, not an instant cutoff. This mirrors the staleness class the app already accepts for `mustChangePassword` and is fine for a vendor-monitored demo.

## 5. UI

- **`/trial-expired`** (new page, styled like `/login`): "Your 30-day trial has ended." The user still has a valid (just `trialLocked: true`) session at this point — the page is a normal server component that calls `getSessionUser()` + `getTrialStatus()` directly to render the machine ID, no separate unauthenticated endpoint needed. Shows a paste-key textarea/file-drop, reusing the existing paste/upload component pattern from `LicenseSection` in `src/components/tabs/SettingsTab.tsx`. On success, reloads into the app.
- **Settings → License & Plan**: while `isTrial && !isLocked`, show a banner "Trial: N days remaining" above the existing license UI. The same paste-key field also accepts the unlock payload here, so a customer can convert **before** expiry without ever hitting the lockout screen.
- `GET /api/license` response gains a `trial: { isTrial, daysRemaining, isLocked, machineId }` field (from `getTrialStatus()`) for both surfaces to consume.

## 6. Build path

New `package.json` script `electron:build:trial` (parallel to `electron:build:base` / `:plus` / `:upgrade`), invoking the existing `scripts/electron-build.js` with flags that set, in the bundled `.env.local`:

```
WVO_IS_TRIAL=true
WVO_DEFAULT_TIER=plus
```

Output: `dist-electron/WhiteVanOps-Trial-Setup.exe`.

## Testing

- Unit tests for `getTrialStatus()` in `src/lib/trial.test.ts` (mirrors `license.test.ts` conventions: mock `fs`, `node-machine-id`, `@/lib/db` per the project's existing Vitest patterns) covering: non-trial no-op, first-read anchor creation, expired-without-unlock → locked, expired-with-unlock → not locked, signature-tamper rejection.
- Unit tests for the new `POST /api/license` `unlock-trial` branch: valid key accepted, wrong-machine key rejected, malformed JSON rejected, tier correctly applied to DB.
- Manual verification pass (documented in the manual, not automated): build the trial installer, fast-forward `installedAt` in a test `trial.json`, confirm lockout, confirm unlock key clears it.
